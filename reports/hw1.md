## 删除、更新与引用所有权

删除先回收完整 tuple 数据范围，再将对应槽标为空。只截去槽数组末尾连续空槽；中间空槽保留原编号，其他 tuple 的外部 FilePointer 因而保持稳定。

NULL 更新移除旧值的物理字节，修正 tuple 起点，设置 bitmap，并重新计算各列偏移。非 NULL 更新先求旧、新编码长度之差，在列起点增删字节，修正起点与写入地址，写入值后重新计算偏移。页内数据向低地址增长，因此扩容量为正时 tuple 起点减小。无需移动到另一数据页；无法在本页容纳的增长抛出异常，未实现跨页转发。

`loadDBPage` 的临时 pin 通过 `finally` 释放，返回的 PageTuple 保留它自己持有的一个 pin。查询评估器消费返回 tuple 后释放，包括 processor 抛异常时；选择节点释放被过滤的 tuple。元数据和索引页面也有成对的加载与释放。直接存储测试绕过 SQL 命令结束时的 `unpinAllSessionPages`，检查返回数据页 pin 为 1、释放后为 0，防止服务器的兜底清理掩盖泄漏。

## 持久化空闲空间目录

设页大小为 S，目录扇出 K=S/2。物理布局为：

- 页 0：文件头，保留前两个官方文件类型和页大小字节；随后存格式标记、持久化页计数、schema/statistics。
- 页 1：根目录，unsigned-short 数组；每项记录一个叶目录的最大插入容量。
- 页 `2+g*(K+1)`：第 g 个叶目录；随后 K 页为对应数据页。数据页本身保留官方 slotted-page 布局。

叶条目存 `freeBytes + (有空槽 ? 2 : 0)`。插入需要 `tupleBytes+2`，因此空槽复用也被精确考虑。0 同时用于尚未分配页和没有可插入容量的页；合法 tuple 至少需要 NULL bitmap，查询阈值为正，不会误选未分配条目。最大页大小 65536 时，容量不超过 65534，可以用两个字节表达。

分配先查根中的首个足够大的最大值，再查对应叶，最后加载目标数据页；找不到时追加。根和叶的容量在插入、删除、更新后维护，不依赖 TableStats 或进程内游标。页计数写入文件头，避免使用尚未刷盘时可能过期的文件长度。扫描和随机引用跳过目录页，关闭重开后直接从磁盘恢复索引。

对既有数据页的插入，目录加载数量固定；目录内搜索仍是数组线性搜索，不能称为对数时间算法。叶最大值重新计算只扫描已分配的条目。每个变更至多写数据页、叶、根三页；追加时还需要更新页计数，跨组时创建新叶。根最大值未变时不写根。元数据与远端数据页之间仍会产生跳转，优化的目标是去掉遍历整个 heap 的读取，实际收益必须以完整脚本计数为准。

格式标记为 `0x48573101`，schema 起点由 6 改为 14。旧数据文件会被明确拒绝，需使用原始 SQL 重建；没有提供在线迁移。目录是教学用存储结构，没有额外声称已完成 HW7 的事务及崩溃恢复。支持地址上限为 65536 页，越界分配拒绝。新增测试实际建立 65279 个单行数据页，加文件头、根和 255 个叶目录，文件恰为 65536 页、33554432 字节；验证最后物理页 65535、满文件追加失败、关闭重开后最后页删除与复用。两套构建均通过，Maven 中此项耗时 9.001 秒。

目录固定开销为两页加每 K 个数据页一页；小表相对开销较大，课程大型性能脚本的文件增长另行测量。

最终完整功能及性能验证：[Actions 41743000142](https://github.com/edidada/caltech-cs122-nanodb-base/actions/runs/41743000142)，提交 `8f97d95844d9420b1cc2b52a0e96a2a6c01da473`。下载原始 XML 核实 Maven、Gradle 各 149 项、失败/错误/跳过均 0；包含原有 144 项及新增 5 项。对应记录见 [完整机器数据](hw1-performance.json)。

新增测试覆盖 512–65536 的全部八种页大小、关闭重开后的容量复用和稳定引用、512 字节页下跨三个叶组的 620 条大记录、64KiB 最小缓存下直接存储访问，以及 20 列跨 NULL bitmap 字节边界的 1500 次固定种子随机更新（含空字符串、增长、缩短、NULL），以及拒绝 500 条记录和 processor 首行抛异常时的 pin 释放。最大页测试使用 1MiB 缓存，最小缓存测试使用 512 字节页；未将它们声称为所有页大小与所有缓存大小的笛卡尔积验证。

性能驱动完整执行官方 `ins20k.sql`、`ins50k.sql`、`ins50k-del.sql`，没有缩减行数。基线固定为 `d93810fc433c948a2f4ff701e28a96319096745a`：保留线性 first-fit，并具有相同的删除、更新与引用修复。双方使用相同驱动、8192 字节页、1MiB 缓存，`flushAfterCmd=true`，关闭键约束检查；不关闭每命令刷盘来美化结果。

记录 pagesRead、pagesWritten、fileChanges、fileDistanceTraveled、文件字节数与耗时。计数在建表刷盘后清零，在工作负载末尾刷盘后截取；验证扫描不计入性能。计时包含 SQL 解析、执行和刷新，不包含 Java 进程启动、建表或最终校验扫描。Python 根据所有 INSERT/DELETE 独立重放存活记录，转换为 IEEE float32，生成最终全表哈希；双方必须与 oracle 一致，不能只比较行数。

早期性能任务在双方全量数据和哈希均正确后，被自定义“距离必须下降”断言拦住；该要求不属于官方题目，官方 C2 反而要求讨论可能增加的寻道。最终保留全部计数，将该自测改为明确的距离增长不超过 5% 回归预算（不是官方评分标准），并仍严格要求全表 oracle 一致、读页减少和文件增长不超过 5%。原先测试 SQL 保留字和负数边界解析问题也已修复，未删去官方工作负载或失败记录来制造通过。

最终存活记录数分别为 20000、50000、36993，完整 SHA-256 见 JSON；基线与索引实现均与 Python 独立重放结果一致。正式课程私有评分、学校提交和其他 HW 不在已完成范围。
