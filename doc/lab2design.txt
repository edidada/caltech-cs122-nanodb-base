A:  Simple Planner
------------------

A1.  Without going into the details of how you handle grouping and
     aggregation or joins, list the general sequence of steps that your
     planner's makePlan() method follows to translate a SQL query into
     an execution plan.

Answer: Validate WHERE/GROUP BY/ON aggregates; recursively build FROM; apply WHERE; build hash grouping/aggregation when needed; apply HAVING; project SELECT values; sort projected rows with ORDER BY; finally apply LIMIT/OFFSET. A query without FROM starts with one empty tuple. prepare() is called before returning the complete plan.

A2.  Does your planner try to simplify plans in specific circumstances,
     e.g. when a "trivial project" is used (i.e. "SELECT * FROM ...") in
     your planner?  Briefly enumerate all simplifications and optimizations
     your planner employs.

Answer: Omit a trivial SELECT * projection. Add filters only when specified, combining WHERE with an existing SelectNode through PlanUtils when safe. Omit grouping, sorting and LIMIT nodes if unnecessary. Equal aggregate calls share one query-local computed column. This is not a cost-based optimizer and does not push WHERE through outer joins.

A3.  Describe how you generate the execution-plan fragment for the query's
     FromClause.  Make sure to touch on what you do in the three cases your
     planner is expected to handle - tables, subqueries in the FROM clause,
     and joins.

Answer: Base tables use the inherited makeSimpleSelect and FileScanNode; derived tables recursively call makePlan; joins recursively build both inputs and use NestedLoopJoinNode with the computed ON predicate. RenameNode implements table/subquery aliases. RIGHT OUTER swaps physical inputs while preserving output order. NATURAL/USING bind columns by resolved tuple/column positions and isolate private input schemas before projecting the public shared-column schema computed by FromClause.

A4.  Describe how you implemented support for grouping and aggregation.
     Be sure to note any variations from the approach outlined in class,
     if there are any.

Answer: AggregateProcessor traverses private expression copies, records FunctionCalls in insertion order, and replaces them with generated #HW2_AGG_n columns. A shared processor handles SELECT and HAVING. It rejects WHERE/ON/GROUP BY aggregates and nested aggregates using InvalidSQLException. GroupReferences maps entire grouping expressions to their output columns, and GroupAggregateNode now accepts expression keys. Hash aggregation creates the global group even for empty input; function state is cleared and DISTINCT sets are independently cloned per group. Projection preserves original output names so ORDER BY aliases resolve correctly. The original SelectClause is unchanged and can be planned repeatedly.

B:  Nested-Loop Join
--------------------

B1.  The join algorithm stated in class is really only suitable for
     materialized evaluation, where the entire result is generated by the
     algorithm.  It is completely unsuitable for pipelined evaluation,
     where results are generated row by row.

Answer: State: leftTuple, child cursors, matchedLeft, done, and emitted count.
  while not done:
    if no leftTuple:
      leftTuple = left.next()
      if EOF: done = true; return EOF
      right.initialize(); matchedLeft = false
    rightTuple = right.next()
    if rightTuple exists:
      if predicate is TRUE:
        matchedLeft = true; return a copied joined tuple
      always release rightTuple after its values have been consumed
    else:
      release leftTuple; clear leftTuple
  The left tuple remains pinned across calls until its right scan finishes.
  Joined results are TupleLiteral copies. cleanUp and initialize release any
  held left tuple. Clones start without sharing the original node's tuple pins.

     Summarize how your implementation works for inner joins, using
     pseudocode to show how rows are considered and returned as the
     algorithm executes, and what state must be saved so that the
     operation can resume at the appropriate place when the next row
     must be returned.

B2.  What tweaks did you need to introduce into the implementation for
     left outer joins?  Keep your answer brief, but please also be specific.

Answer: Track whether the current outer row matched at least once. At inner EOF, emit exactly one joined copy with an all-NULL right tuple only if no match occurred, then release the outer row. RIGHT OUTER uses the same logic after swapping input nodes and preserving the original output schema order. SQL UNKNOWN does not match.
