A1.  Using pseudocode, summarize the implementation of your HeapTupleFile
     analyze() function.  Please summarize your actual code; do not simply
     paste in the assignment description or the actual code you wrote.

Answer:
Create one ColumnStatsCollector per schema column; read the persistent page count; visit every allocated data page once, skipping root/leaf metadata; sum packed tuple bytes; visit only occupied slots, feed values to collectors, and release tuple/page pins in finally. Construct TableStats with data-page count, tuple count, zero-safe average and collected columns; saveMetadata persists it. Do not use getFirstTuple/getNextTuple.


B:  Plan Costing Estimates
----------------------------------------

B1.  Briefly describe how you estimate the number of tuples and the cost
     of a file-scan plan node.  What factors does your cost include?

Answer:
Output rows = table rows * predicate selectivity; tuple size = measured average; CPU = input table rows; best-case block IO = data pages, large seeks = one for nonempty file. Metadata-directory pages are excluded from data-page statistics, consistent with the HW1 format.


B2.  Briefly describe how you estimate the number of tuples and the cost
     of a simple-filter plan node.  What factors does your cost include?

Answer:
Output rows = child output rows * selectivity; CPU = child CPU + child output rows; tuple size, block IO and seeks inherit the child. StatisticsUpdater returns deep copied narrowed columns.


B3.  Briefly describe how you estimate the number of tuples and the cost
     of a nested-loop join plan node.  What factors does your cost include?

Answer:
Pairs=L.rows*R.rows; inner rows=pairs*selectivity; left outer rows=max(L.rows,inner estimate). RIGHT is physical swapped LEFT with preserved output order. CPU=L.cpu+L.rows*R.cpu+pairs. Best-case IO assumes sufficient memory and reads each child once, skipping inner IO if the outer is empty. These are approximate costs, not observed physical IO. Key-based costing is not implemented.


B4.  For each kind of comparison (==, !=, >, <, >=, <=), how do you update the
     estimated number of distinct values for each kind of comparison that your
     StatisticsUpdater implementation supports?  Are there cases where you make
     no changes to the statistics?

Answer:
Equality sets distinct to one, or zero for an impossible domain. Inequality != removes one estimated distinct value when the excluded value can be present. Numeric ranges scale known distinct count by the uniform selectivity, round up, clamp to the old count and retain at least one for a nonempty domain. Unknown counts remain unknown; unsupported predicates leave statistics unchanged. Comparisons remove NULLs. Contradictory domains become zero distinct with no min/max.


B5.  For each kind of comparison (==, !=, >, <, >=, <=), how do you update the
     estimated min and max values for each kind of comparison that your
     StatisticsUpdater implementation supports?  Are there cases where you make
     no changes to the statistics?

Answer:
Equality sets numeric/orderable min=max=literal. Range bounds intersect the old envelope with the literal; strict bounds retain the endpoint approximation instead of inventing a successor observed value. != retains bounds because the next observed endpoint is unknown. Strings have no stored min/max. OR/NOT and unsupported predicates do not narrow domains. Input statistics and expressions are not mutated.
