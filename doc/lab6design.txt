CS122 Assignment 6 - B+ Tree Indexes - Design Document
======================================================

A:  Analysis of Implementation
------------------------------

Given NanoDB's B+ tree implementation, consider a simple schema where an
index is built against a single integer column:

     CREATE TABLE t (
         -- An index is automatically built on the id column by NanoDB.
         id INTEGER PRIMARY KEY,
         value VARCHAR(20)
     );

Answer the following questions.

A1.  What is the total size of the index's search-key for the primary-key
     index, in bytes?  Break down this size into its individual components;
     be as detailed as possible.  (You don't need to go lower than the
     byte-level in your answer, but you should show what each byte is a
     part of.)

Answer A1: The stored full index tuple is 9 bytes: one NULL bitmap byte
for two columns, four bytes for the non-NULL INTEGER id, and four bytes
for the table-row FilePointer (two-byte page number + two-byte offset).
The pointer is part of the complete key, distinguishing equal indexed
values in non-unique indexes. No per-tuple slot-directory entry is stored.

A2.  What is the maximum number of search-keys that can be stored in leaf
     nodes of NanoDB's B+ tree implementation?  You should assume a page-
     size of 8192 bytes.

Answer A2: LeafPage.OFFSET_FIRST_TUPLE is 5: one page-type byte, two
next-leaf bytes, two tuple-count bytes. floor((8192-5)/9)=909 full keys
fit (8181 key bytes, 6 unused bytes). This assumes the stated INTEGER
primary key and non-NULL FilePointer, not arbitrary variable-width keys.

A3.  What is the maximum number of keys that can be stored in inner nodes
     of this particular implementation?  (Recall that every key must have
     a page-pointer on either side of the key.)

Answer A3: InnerPage.OFFSET_FIRST_POINTER is 5. For k keys there are
k+1 two-byte child pointers, so 5+9k+2(k+1)<=8192. Therefore
floor((8192-7)/11)=744 keys, with 745 pointers, consume 8191 bytes.
The child page pointer (2 bytes) differs from a row FilePointer (4 bytes).

A4.  In this implementation, leaf nodes do not reference the previous
     leaf, only the next leaf.  When splitting a leaf into two leaves,
     what is the maximum number of leaf nodes that must be read or written,
     in order to properly manage the next-leaf pointers?

     If leaves also contained a previous-leaf pointer, what would the
     answer be instead?

     Make sure to explain your answers.

Answer A4: At most two leaf pages: old L and new R. R.next takes
old L.next, then L.next becomes R. The former successor is untouched.
With previous links, at most three leaf pages are needed: L, R, and the
former successor whose prev must become R. Parent/header pages are
separate and are not included in this leaf-only count.

A5.  In this implementation, nodes do not store a page-pointer to their
     parent node.  This makes the update process somewhat complicated, as
     we must save the sequence of page-numbers we traverse as we navigate
     from root to leaf.  If a node must be split, or if entries are to be
     relocated from a node to its siblings, the node’s parent-node must
     be retrieved, and the parent’s contents must be scanned to determine
     the node’s sibling(s).

     Consider an alternate B+ tree implementation in which every node
     stores a page-pointer to the node’s parent.  In the case of splitting
     an inner node, what performance-related differences are there between
     this alternate representation and the given implementation, where
     nodes do not record their parents?  Which one would you recommend?
     Justify your answer.

Answer A5: Persistent parent pointers cost space in every node and
require changing the parent pointer of each child transferred to a new
inner sibling. Splitting a high-fanout node can dirty/read hundreds of
child pages even though their keys did not change. The stack/path scheme
retains O(height) page numbers and revisits the parent, scanning its
entries to find siblings, but avoids these child-page writes. For this
buffered insertion/deletion design I prefer the path scheme; parent
pointers may help upward navigation but are not free I/O optimization.

A6.  It should be obvious how indexes can be used to enforce primary keys,
     but what role might they play with foreign keys?  For example, given
     this schema:

     CREATE TABLE t1 (
         id INTEGER PRIMARY KEY
     );
     CREATE TABLE t2 (
         id INTEGER REFERENCES t1;
     );

     Why might we want to build an index on t2.id?

Answer A6: An index on referencing t2.id locates all dependent rows
when t1.id is deleted or changed, allowing RESTRICT checks or CASCADE
actions without scanning all of t2. Cost becomes an index descent plus
the matching range rather than O(|t2|). It does not itself enforce the
foreign key; event/constraint logic must still probe and apply the policy,
and t2 writes must maintain this additional index.

A7.  Over time, a B+ tree's pages, its leaf pages in particular, may become
     severely out of order, causing a significant number of seeks as the
     leaves are traversed in sequence.  Additionally, some of the blocks
     within the B+ tree file may be empty.

     An easy mechanism for regenerating a B+ tree file is to traverse the file's
     tuples in sequential order (i.e. from the leftmost leaf page, through
     all leaf pages in the file), adding each tuple to a new B+ tree file.
     The new file may then replace the old file.

     Imagine that this operation is performed on a B+ tree file containing
     many records, where all records are the same size.  On average, how full
     will the leaf pages in the newly generated file be?  You can state your
     answer as a percentage, e.g. "0% full".  Explain your answer.

A8.  Consider a variation of the approach in A7:  Instead of making one pass
     through the initial B+ tree file, two passes are made.  On the first pass,
     the 1st, 3rd, 5th, 7th, ... tuples are added to the new file.  Then, on the
     second pass, the 2nd, 4th, 6th, 8th, ... tuples are added to the new file.
     On average, how full will the leaf pages in the newly generated file be?
     Explain your answer.

Answer A7: Approximately full for large equal-size records in this
implementation, rather than the 50% average of split-only insertion. On
ascending insertion, a full rightmost leaf first moves its smallest tuples
to the left sibling before splitting, progressively filling that sibling.
The relocation code reserves extra space conservatively; the rightmost leaf
and leaves adjacent to parent-boundary splits can remain partly filled.
Thus there is no exact universal percentage independent of key width,
fanout and record count. In the actual 6000-row, INTEGER+CHAR(128), 8192-byte
page experiment, 102 leaves contain 798000 tuple bytes out of 835584 page
bytes: 95.502068% mean (minimum 63.317871%, maximum 99.035645%).

Answer A8: Also high occupancy here, not a guaranteed doubling of an assumed
50%-full first pass. The odd-key pass already fills most leaves using left
relocation; the even-key pass therefore causes further relocation/splits.
Its final distribution depends on parent boundaries and the finite tail.
The same actual dataset produces 103 leaves and 798000/843776=94.574863%
mean (minimum 50.329590%, maximum 99.035645%). These are measured examples,
not a claim that every two-pass rebuild has that exact occupancy. The ideal
near-full asymptote is constrained by per-page header/key rounding and the
implementation's reserved relocation space. Source and provenance are in
reports/hw6-occupancy.json, Actions 41863122155. This individual experiment
passed in a run whose overall suite still had four unrelated failures;
it does not constitute whole-assignment acceptance.
